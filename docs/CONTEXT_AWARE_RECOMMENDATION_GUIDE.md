# 상황 기반 추천 가이드

`[권장]` 날씨·시간·재고 같은 바깥 상황을 추천에 반영하는 방법과 한계.

## 왜 쓰나

같은 사람이라도 **비 오는 날 점심시간**과 **한가한 오후**에 원하는 것이 다릅니다.
사용자에게 다시 묻지 않고도 순서를 바꿔줄 수 있다면 입력 부담이 줄어듭니다.

## 쓸 수 있는 맥락

| 종류 | 예 | 얻는 곳 |
| --- | --- | --- |
| 날씨 | 비·눈·맑음 | 날씨 API |
| 기온 | 폭염·한파 | 날씨 API |
| 시간대 | 오전·점심·저녁 | **기기 시계** (API 불필요) |
| 요일 | 평일·주말 | 기기 시계 |
| 공휴일·명절 | 추석·설날 | 공휴일 API 또는 달력 데이터 |
| 계절 | 여름·겨울 | 기기 시계 |
| 지역 행사 | 축제 기간 | 직접 입력 또는 API |
| 재고·품절 | 준비 안 됨 | **fixture 의 `available`** |
| 대기시간·혼잡도 | 지금 붐빔 | 매장 API 또는 시간대 추정 |
| 사용자가 저장한 선호 | 지난번 크기 | 기기 저장소 |
| 사용자가 고른 관심 업무 | 자동차 관련 | 사용자 입력 |

**시간대와 재고는 외부 API 없이도 됩니다.** 여기서 시작하세요.

## 예시

| 상황 | 반영 | 사용자에게 보여줄 이유 |
| --- | --- | --- |
| 비 오는 날, 음식점 | 따뜻한 것을 앞으로 | "지금 비가 내려 따뜻한 메뉴를 먼저 보여드립니다." |
| 폭염 | 차가운 것 / 짧은 대기 | "오늘 많이 더워 시원한 메뉴를 앞에 두었습니다." |
| 추석, 떡집 | 명절 상품을 앞으로 | "추석이라 송편을 먼저 안내드립니다." |
| 점심 혼잡 | 빨리 나오는 것 | "지금 붐벼서 빨리 받으실 수 있는 것을 먼저 보여드립니다." |
| 관공서, 자동차 관심 선택 | 관련 업무 안내 | "자동차 관련 업무를 고르셔서 등록증 발급을 함께 안내드립니다." |

마지막 예시를 주의 깊게 보세요. **사용자가 직접 고른 관심사**를 반영한 것이지,
차를 가지고 있는지 **추론한 것이 아닙니다.**

## 절대 하면 안 되는 것

| 금지 | 이유 |
| --- | --- |
| 병원에서 증상·날씨로 진료과 추론 | 의료 판단입니다 |
| 관공서에서 자격·수급 가능성 판단 | 행정·법률 판단입니다 |
| 외부 맥락으로 hardConstraint 무시 | 알레르기는 날씨보다 우선합니다 |
| 만료된 데이터로 자동 진행 | 어제 날씨로 오늘을 정하지 마세요 |
| 추천을 곧바로 실행 | 항상 사용자 확인을 거칩니다 |
| 이유를 숨기고 순서만 바꾸기 | 사용자가 왜 그런지 알 수 없습니다 |

### hardConstraint 우선순위

```
hardConstraints (알레르기·예산·인증수단)   ← 절대 양보 없음
    ↓
facts (재진·예약·진료과)                   ← 사실이므로 양보 없음
    ↓
preferences (크기·맵기)                    ← 양보 가능
    ↓
외부 맥락 (날씨·혼잡도)                    ← 순서 조정에만 사용
```

외부 맥락은 **정렬 순서를 바꿀 뿐**, 후보를 걸러내는 기준이 아닙니다.

## Contract 연결

Core 계약을 바꾸지 않습니다. **팀 namespace 아래 extensions** 로만 넣습니다.

```json
{
  "sessionContext": {
    "intent": { "task": "ORDER_FOOD" },
    "facts": {},
    "preferences": { "serviceType": "TAKE_OUT" },
    "hardConstraints": { "allergenIds": ["PEANUT"] },
    "capabilities": {},
    "fieldMetadata": {},
    "extensions": {
      "TEAM_001.contextSignals": [
        {
          "type": "WEATHER",
          "key": "condition",
          "value": "RAIN",
          "source": "WEATHER_API",
          "observedAt": "2026-08-03T00:00:00Z",
          "expiresAt": "2026-08-03T01:00:00Z",
          "confidence": 1
        }
      ]
    }
  }
}
```

### 필드 규칙

| 필드 | 필수 | 규칙 |
| --- | --- | --- |
| namespace | 예 | `TEAM_XXX.` 로 시작 |
| `type` | 예 | `WEATHER` · `TIME_OF_DAY` · `HOLIDAY` · `CROWDING` · `STOCK` 등 |
| `key` | 예 | 어떤 항목인지 |
| `value` | 예 | 값 |
| `source` | 예 | 어디서 왔는지 (`WEATHER_API` · `DEVICE_CLOCK` · `MOCK_*`) |
| `observedAt` | 예 | **UTC ISO 8601** (`2026-08-03T00:00:00Z`) |
| `expiresAt` | 권장 | 언제까지 유효한지 |
| `confidence` | 권장 | 0~1 |

### extensions 가 할 수 없는 것

- Core 필드 덮어쓰기
- Safety Rule 우회
- hardConstraint 무시
- 실제 개인정보 저장
- 공식 enum 임의 변경

`inputContractVersion` 은 **바뀌지 않습니다.** extensions 는 원래 자유 영역입니다.

## 만료 처리

```
observedAt 이 1시간 전 날씨 → 쓰지 마세요
expiresAt 이 지난 재고 정보  → 쓰지 마세요
```

만료된 맥락은 **없는 것으로 취급**하고, 추천 이유에서도 언급하지 마세요.
"오래된 정보라 반영하지 않았습니다" 라고 알려주는 것도 좋습니다.

## API 가 없어도

외부 API 없이 만들 수 있는 맥락:

- 시간대 · 요일 · 계절 → 기기 시계
- 재고 · 품절 → `fixture.candidates[].available`
- 사용자가 저장한 선호 → 기기 저장소
- 사용자가 고른 관심 업무 → 입력

심사를 위해 유료 API 에 가입할 필요가 없습니다.
**Mock 데이터로도 충분히 보여줄 수 있고**, 그 경우 `source` 에 `MOCK_*` 이라고 밝히세요.

## 로그인·저장·개인정보 정책

| 구분 | 내용 |
| --- | --- |
| Example UI | 로그인 없이 동작하는 **Sandbox 참고 예제**입니다. 공식 정답이 아닙니다. |
| 참가팀 자유 | 로그인, 기기 내 프로필 저장, QR, 음성, 카메라, OCR, 보호자 입력 등을 **선택적으로 자유롭게** 구현할 수 있습니다. |
| 반드시 지킬 것 | 로그인 기능은 금지되지 않지만, **로그인하지 않아도 서비스의 핵심 기능을 사용할 수 있어야 합니다.** |
| 심사 데이터 | 해커톤·심사·시뮬레이션에서는 실제 개인정보가 아닌 **가상·합성 데이터**를 사용해야 합니다. |
| 실제 서비스 확장 | 실제 서비스에서 개인정보를 처리하려면 별도의 동의, 최소수집, 저장기간, 삭제, 보안 정책이 필요합니다. |
